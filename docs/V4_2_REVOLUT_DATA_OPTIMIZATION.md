# V4.2 public market-data optimization

The acquisition path remains public read-only REST. The current [official Revolut X API documentation](https://developer.revolut.com/docs/api/revolut-x-crypto-exchange) specifies one request per second for each public endpoint family and numeric Retry-After delays in milliseconds. The existing millisecond interpretation is preserved. Public authenticated market-data/FIX references do not establish an available, documented unauthenticated WebSocket feed with the required recovery contract; no unsupported streaming integration was invented.

`MarketDataService.completed_candles` caches completed observations by symbol/interval/lookback and current 5-minute boundary. Refreshes request one overlapping prior bar plus newly available observations, merge by timestamp, retain a bounded history and validate before publishing. The official PostgreSQL SystemState store coordinates refresh leases and cached payloads between API/worker instances. No network request occurs while a database lock is held. An in-progress refresh without a current completed cache defers the competing acquisition. Failed/invalid refreshes are not promoted to valid cached data.

The primary strategy feature window remains 240 bars. Experiments acquire a shared 720-bar warm window for complete 15m/1h context, then fetch incrementally. The scanner and all shadow strategies reuse that cross-section. Protective monitoring shares one book per symbol per cycle, preserves its native timestamp and revalidates every use. A 91-second-old cached book is rejected; cache reuse never makes a stale quote fresh.

The request client uses a priority gate: protective book requests precede queued discovery requests at the next request boundary. In-flight HTTP cannot be preempted. PostgreSQL pacing and a bounded pending-protection reservation coordinate processes. HTTP429 increments breaker failures, publishes a shared cooldown, respects Retry-After, and applies bounded exponential backoff with jitter. Four unsuccessful attempts or a long cooldown defer the cycle. Persistent counters expose 429s, successes/failures, request time including pacing, refreshes, downloaded candles, cache hits, timestamps and ages through authenticated `/api/market-data/health` and System Health.

Executed deterministic measurement: ten one-minute scans required **2 candle requests and 243 downloaded candles**, versus the previous **10 full-window requests and 2,392 candles**: 80% fewer candle calls and 89.84% fewer downloaded records after accounting for the initial warm request. A separate service instance reused the same PostgreSQL cache without another fetch. These are controlled measurements, not a claimed measured production 429 reduction.

Independent genuine public smoke: BTC-EUR, ETH-EUR and SOL-EUR each produced GOOD observations on two scans, with 719 complete cached candles per asset and native public books. There were ten successful HTTP requests (one pair configuration, six book snapshots and three initial candle fetches), zero observed429s and zero submitted orders. The short sample cannot establish long-term provider availability. Raw evidence: `evidence/v4_2-public-market-smoke.json`.

Executed tests cover incremental request bounds, shared cache reuse, native quote-age rejection, cooldown/priority across repository clients, 1500ms Retry-After, exponential retry floors, retry exhaustion and breaker refusal. Additional existing public-data/accounting regressions: 43 passed. No guarantee of a live-market trade follows from a successful data smoke.

Circuit breakers are separated by endpoint family: a failed candles endpoint does not open the healthy order-book circuit. The final regression tests exercise this protective availability boundary.

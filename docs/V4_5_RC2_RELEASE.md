# AutoTrader V4.5 RC2 — Stage A

This release preserves existing execution identities and adds durable execution observations. Stage A includes local implementation, tests, immutable packaging and GitHub publication. It does not authorize deployment. The exact commit, archive SHA-256 and source fingerprint are supplied by the immutable release manifest and the delivery record generated after committing; they cannot be embedded in their own commit.

## Confirmed cause and correction to RC1

RC1's written assertion that the four accepted A2 decisions produced no orders was incorrect. Its committed raw observations already contain four REJECTED orders. The RC2 read-only audit matched all four decision IDs to their persisted orders and their original timestamps. On 18 October at 13:08 UTC, production contained 13 rejected A2 BUY orders, zero fills and zero open positions across all nine accounts. Each rejection records `execution_quality:first_target_destroyed_by_execution_costs`. Twelve were already present at the initial RC2 snapshot; the existing worker added one while Stage A continued.

The saved order payloads retain the submitted books, quantity, fees, slippage, targets and quality results. Running the exact original V4.4 quality engine on these inputs reproduces the entry VWAP, fee, executable quantity, allocations, target scenarios, breakeven and rejection reasons. The four original first targets were only about 14–18 basis points away; modeled fee/slippage alone were about 36 basis points round trip. Rejecting these proposals was expected behavior. Historical price-step/minimum-order metadata and target-hit probabilities remain unavailable; conditional target payoffs are not expected returns.

The independent V4.4 telemetry defect is also confirmed: the 35-character `DECISION_ACCEPTED_PENDING_EXECUTION` value exceeds the 32-character database column. The old handler caught that failure, so it does not explain the absence of fills. Missing historical progression events remain missing. The UI retains **Historical execution outcome not verified** as the historical trace assessment and shows independently verified order outcomes separately. No historical trace events are manufactured.

## Execution, monitoring and financial protection

Traces persist actual progression from eligible signal through decision, allocation, preflight, order, fill, opened/protected/closed position. Stable keys and PostgreSQL advisory locks prevent duplicate or regressed events. Short state values fit the existing schema. ATTEMPTED without a result remains unavailable after a crash; an actual refusal or exception distinguishes subsequent never-reached stages from missing historical telemetry. Observer failures are logged and surface as sticky runtime incidents without changing financial return values or safeguards.

Authenticated bounded APIs page decisions and trace events. The established light UI retains Overview, Experiments, Trades, Research and Advanced navigation, includes archived accounts, reports incompatible execution as critical, and separates scanner heartbeat, live cache freshness, 429s, actual order outcomes and unknown stages. Mobile tables scroll inside their panel. Real compiled-React proofs display five persisted fills and a closed position after partial target execution and worker restart for each supported generation.

The backup workflow discovers the official account and every registered shadow, including archives. It rejects missing identities, provisioning states, collisions and marker/manifest mismatches. Private unique backups are checksum verified and parsed, restored on an internal network with the original database names, and independently checked by the actual AMD64 candidate and exact current V4.4 rollback image. All nine have schema `0011_v42_shadow_isolation`, exactly one €500 funding event, unchanged financial seals and valid reconciliation. The verifier never initializes accounts, funds them, starts workers or migrates a restored clone. A genuine nine-database backup discovery exercise also runs inside that isolated cluster.

The production source hash comparison matches the original V4.4 execution files. Production's old `__init__.py` version string differs from Git baseline; it is outside the historical execution closure and is disclosed rather than silently treated as application provenance. No production source, credential, service, configuration, manifest or financial record was changed by Stage A. Existing workers continued adding valuation/risk observations and one rejected order; the dated snapshots explicitly disclose those changes. Core funding, balances, fills, positions, reservations and exit plans remain unchanged. Private dumps and image exports remain outside Git.

## Research verdict and limits

No strategy passed validation and no strategy is promoted. The eight-symbol 5m study retains A2 out-of-sample loss of €11.18 across 27 closed positions and B2 loss of €1.04 across two. C2/E2 have no closed positions in that sample. Larger targets are separate train-selected research hypotheses, never changes to frozen manifests. Separate original V4 strategies at 15m/1h also lose out of sample; they are not relabeled A2/B2 implementations.

Reports retain chronological splits, purge/embargo, four walk-forward windows, trading costs, drawdown, risk-adjusted returns, rejection frequency and conservative multiple-comparison handling. Available assets are current surviving Coinbase EUR proxies; missing observations, absent historical exchange L2, limited regime coverage and the lack of an untouched holdout prevent a profitability conclusion. Broader volatility/cost-distance screens are not counts of eligible trades. Synthetic positive lifecycles prove engineering liveness only. Existing accounts remain unvalidated; stopping, replacing, funding, promoting or expanding them requires separate authority.

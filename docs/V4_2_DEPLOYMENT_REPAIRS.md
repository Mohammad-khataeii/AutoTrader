# V4.2 deployment repairs

`Dockerfile.backend` copies only allowlisted source/configuration. It sets pyproject.toml, requirements.lock and alembic.ini to0644, source/migration directories to0755 and their files to0644 before installing the package. Host0600 permissions therefore cannot make application metadata unreadable to UID10001. Source remains root-owned and unwritable by that user; no secret, environment file, SSH material, dump or data directory is chmodded or copied into the image.

Executed Linux reproduction: a separate build context gave every copied file mode0600 and directories0700. The image built successfully; under `--read-only --cap-drop=ALL --security-opt=no-new-privileges`, UID10001 imported AutoTrader and read `/app/pyproject.toml` (0644), while `os.access(..., W_OK)` was false.

`deploy/vps.py database_state` inspects actual PostgreSQL tables and Alembic state after the owned PostgreSQL/Redis services are healthy. An empty database is FRESH; a migrated database with no accounts, balances or journal is SCHEMA_ONLY; financial records make it POPULATED. Nonempty unversioned or missing-revision databases fail closed. A running PostgreSQL container alone no longer triggers an Alembic lookup/financial backup before initialization.

The up path migrates fresh/schema-only state before application startup; initialized state requires a parsed backup archive and isolated full restore/reconciliation. Account initialization retains its PostgreSQL advisory lock, initial EUR 500 restriction and single funding event. No volume is removed. The upgrade path builds application images before interruption, preserves current PostgreSQL/Redis images, stops only this project's writers, creates/restores a backup, checks migration plus safe empty-registry downgrade/reupgrade on the restored database, and only then migrates production. Core services start without recreating database/cache dependencies. Old images remain retained.

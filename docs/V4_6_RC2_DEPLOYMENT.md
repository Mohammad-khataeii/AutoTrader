# V4.6 RC2 deployment and rollback guide

This is a prepared procedure, **not deployment approval**. Stage A makes no production changes. Stage B requires the user's separate approval of the exact full commit recorded in the immutable package and tag `v4.6.0-rc.2`. Never reuse approval for a correction commit.

This candidate's production preflight is **BLOCKED** because fresh production access and verification were unavailable. Do not attempt activation of this package even after approval alone. Restore access, complete the missing local verification, and publish newly committed, source-bound readiness evidence in a separately identified release. Never patch the packaged evidence on the VPS, overwrite RC2, or bypass the preflight. The steps below apply only once that release passes its preflight and receives exact-commit approval.

1. Verify the local archive SHA-256 and extract it to a new release directory. Run `deploy/release.py verify` using its included manifest and full approved commit. The manifest binds every packaged source file. Run `verify_release_preflight` on that extracted directory; RC2 must use its own source-bound reports. Confirm the branch and tag resolve to the approved commit. Never patch source on the VPS.
2. Identify the current server, application directory, Compose project `autotrader-v41`, image IDs, source identity, schema, services, loopback ports and production URL. Inventory the official account and every retained/archived experiment, manifest, funding, open order, reservation, position, protective stop and target. Record Nginx/TLS configuration hashes and unrelated projects. Do not copy `.env` or credentials away from the VPS; never open SSH private keys.
3. Run the existing project-scoped backup command in `deploy/vps.py`. `deploy/financial_set.py` must discover all nine retained databases, including archived accounts. Require checksums, complete archive parsing, immutable manifests and financial seals. Retain source backups and the current rollback images. A backup from Stage A does not replace a fresh Stage B backup.
4. Restore that exact backup set inside an isolated internal network. Use the exact AMD64 candidate and known-good rollback image IDs with the existing restore verifier. Require account/registry/manifest equality, one funding event per account, schema compatibility, unchanged journal/order/fill/position/reservation seals and empty reconciliation errors under both images. Stop on any failed backup, restore, migration, protection or reconciliation check. Do not start research workers or generate funding on restored production clones.
5. Build or load candidate images from the verified source and record their immutable IDs and application/execution fingerprints. Confirm AMD64 and non-root access to the bundled RC2 comparison. This release requires no new database migration; unexpected schema differences block deployment. Preserve PostgreSQL/Redis volumes, existing ports, Nginx/TLS, URL and all unrelated services.
6. During the approved scoped update, use `deploy/vps.py` with `--project autotrader-v41`, the server's existing environment file, `--release-commit FULL_COMMIT` and `--release-manifest VERIFIED_MANIFEST`. Review its generated Compose override and recorded image release metadata before applying it. Update only the application services required by that exact release, including the research worker if its shared backend image changes. Keep protective monitoring available during the change; quiesce new entries using existing scoped controls if the verified deployment procedure requires it. Never use global prune or `down -v`.
7. Verify backend readiness, worker/coordinator and scanner heartbeats, protective monitoring, Redis and PostgreSQL health. Require simulated mode and real-money execution disabled, all eight old manifests compatible, all nine accounts reconciled and every open position protected. Verify that current five-minute research, stale snapshot quotes and worker/scanner health are displayed separately. Check Personal Plan login, Overview, Opportunities, Strategies, Activity, Research, Decision Insights and Settings on desktop/mobile. Confirm rejection attribution and actual order/fill history. No RC2 strategy receives a new account, capital, promotion or authority automatically.
8. Preserve scoped diagnostics and release/image identities. Clean up only owned temporary release/verification resources after verification succeeds. Retain required rollback images, backups, financial history and immutable research evidence.

## Rollback

Stop and preserve diagnostics on failure. Use the existing `deploy/vps.py rollback --release PREVIOUS_VERIFIED_RELEASE_JSON` flow, with the required full commit and manifest for source operations. Check its recorded previous image IDs before the scoped restart. Do not substitute mutable image tags or replace production branches. An application/image rollback does **not** authorize restoring an older database over newer transactions. Restore financial data only through a separately reviewed recovery plan that accounts for all transactions since backup; never blindly overwrite current history. This candidate has no schema migration, so a normal rollback should retain current databases and use verified prior images. Reconcile all nine accounts and protection state after recovery.

Any application correction must be developed, tested, committed, pushed and packaged locally and receive fresh approval before another deployment attempt.
